Scope: the six sections in `content/modules/m03/meta.json`, at the level of a certification study guide:
definitions, recognition of scan types and tools by name and purpose, what each reply means, and how a
defender detects and limits scanning. The public CEH v13 course page gives the module's topic names (scope

a defender must recognise and detect, not as procedures.

or a tool's own reference guide is the authority on its own content). **verify** marks EC-Council framing

## Network Scanning Concepts

| Fact | Sources | verify |
|---|---|---|
| Scanning follows footprinting: footprinting gathers what is public (domains, IP ranges, people) with little or no contact; scanning sends packets to those ranges to learn which hosts are live, which ports are open, which services and OS run. It is active, so the target can see and log it. | NIST SP 800-115 §4.1–4.2 (network discovery, port and service identification); MITRE T1595 (Active Scanning, "probe victim infrastructure") | no |
| NIST SP 800-115 groups target identification and analysis as network discovery, network port and service identification, vulnerability scanning, and wireless scanning. | NIST SP 800-115 §4; NIST glossary "network discovery", "port scanning" | no |
| EC-Council's scanning steps: check for live systems, discover open ports, discover services and versions, discover the OS (banner grabbing), scan beyond IDS/firewalls, draw network diagrams. | EC-Council CEH page (module topic names); NIST SP 800-115 §4 (same activities, different grouping) | **yes** |
| ATT&CK: T1595 Active Scanning (Reconnaissance tactic, from outside: .001 Scanning IP Blocks, .002 Vulnerability Scanning, .003 Wordlist Scanning); T1046 Network Service Discovery (Discovery tactic, from inside a compromised network); T1018 Remote System Discovery (finding other hosts from inside). | attack.mitre.org T1595, T1046, T1018 pages | no |
| TCP three-way handshake: SYN → SYN/ACK → ACK. A closed port answers a SYN with RST (RST/ACK). A connection ends with FIN exchanges or is aborted with RST. | RFC 9293 §3.5 and §3.10.7; Nmap "TCP SYN (Stealth) Scan" chapter | no |
| The six classic TCP control flags: URG (urgent pointer valid), ACK (acknowledgment valid), PSH (push data to the application), RST (reset the connection), SYN (synchronise sequence numbers), FIN (no more data from sender). RFC 9293 lists two more, CWR and ECE, added for ECN by RFC 3168. | RFC 9293 §3.1 (control bits); RFC 3168 §6.1 | no |
| RFC rule used by several scans: a closed port answers any segment that is not a RST with a RST; an open port silently drops a segment that has none of SYN, RST or ACK set. | RFC 9293 §3.10.7.1–3.10.7.2; Nmap NULL/FIN/Xmas chapter (quotes RFC 793 p. 65) | no |
| UDP is connectionless: no handshake and no flags. A closed UDP port normally triggers ICMP port unreachable (type 3 code 3); an open one may reply or stay silent. | RFC 768; RFC 1122 §4.1.3.1; Nmap UDP scan chapter | no |
| ICMP types seen in scanning: 0 echo reply, 3 destination unreachable (code 0 net, 1 host, 2 protocol, 3 port, 4 fragmentation needed with DF set; 9, 10, 13 administratively prohibited), 5 redirect, 8 echo request, 11 time exceeded (used by traceroute), 12 parameter problem, 13/14 timestamp request/reply, 17/18 address mask request/reply (deprecated by RFC 6918). | RFC 792; IANA ICMP parameters; RFC 950; RFC 6918 | no |
| Port numbers (IANA, RFC 6335): 0–1023 system (well-known), 1024–49151 user (registered), 49152–65535 dynamic/private. | RFC 6335 §6; IANA port registry | no |
| Common ports the exam leans on: 21 FTP, 22 SSH, 23 Telnet, 25 SMTP, 53 DNS (UDP and TCP), 67/68 DHCP, 69 TFTP, 80 HTTP, 110 POP3, 123 NTP, 135 MS RPC, 137–139 NetBIOS, 143 IMAP, 161/162 SNMP (UDP), 389 LDAP, 443 HTTPS, 445 SMB, 1433 MS SQL, 3306 MySQL, 3389 RDP. | IANA port registry; Nmap `nmap-services` (via reference guide "Port Specification") | no |
| Scanner families by name: Nmap (reference scanner, host/port/service/OS discovery, NSE scripts, Zenmap GUI), hping3 (command-line packet assembler/analyser: TCP, UDP, ICMP, raw IP; firewall testing, traceroute, IP ID observation), Masscan and ZMap (very fast Internet-scale scanners), Unicornscan, RustScan, Angry IP Scanner (GUI ping/port scanner), Scapy and Colasoft Packet Builder (packet crafting). | nmap.org; kali.org tool pages (hping3, masscan, unicornscan, rustscan, scapy); zmap.io; angryip.org; colasoft.com | no |
| hping3 modes: TCP by default; `-0` raw IP, `-1` ICMP, `-2` UDP, `-8` scan mode, `-9` listen mode; TCP flag options `-S` SYN, `-A` ACK, `-F` FIN, `-R` RST, `-P` PSH, `-U` URG, `-X`/`-Y` the extra bits. | Kali hping3 page (man page text); hping3 `--help` summary on the same page | no |
| Network diagrams: after scanning, the tester (or defender) draws the topology found: live hosts, gateways, firewalls, subnets. Traceroute (ICMP time exceeded) reveals hops and filtering devices; Zenmap has a topology view. EC-Council treats "draw network diagrams" as its own scanning step and names commercial topology mappers. | Nmap Zenmap chapter ("Topology"); RFC 792 (time exceeded); EC-Council CEH page (topic name) | **yes** (EC step and tool list) |
| AI in scanning (CEH v13 framing): AI assistants that generate or explain scan commands and summarise results. | EC-Council CEH page (v13 "AI-powered" framing) | **yes** |

## Host Discovery

| Fact | Sources | verify |
|---|---|---|
| Host discovery (a "ping scan" or ping sweep) finds which addresses in a range are live before port scanning. Nmap does host discovery then port scans live hosts by default; `-sn` stops after discovery; `-Pn` skips discovery and treats every target as up; `-sL` only lists targets (reverse DNS) and sends nothing to them. | Nmap reference guide "Host Discovery"; Nmap book "Host Discovery Controls" | no |
| Nmap default discovery probes (privileged, IPv4, off-LAN): ICMP echo request, TCP SYN to 443, TCP ACK to 80, ICMP timestamp request (= `-PE -PS443 -PA80 -PP`). Unprivileged users: connect() to 80 and 443. On a local Ethernet segment Nmap uses ARP (IPv4) or Neighbor Discovery (IPv6) instead. | Nmap reference guide "Host Discovery"; Nmap book "Host Discovery Techniques" | no |
| ARP ping (`-PR`): ARP request for each IP on the local segment; any ARP reply = host up. Hosts must answer ARP to use the LAN, so host firewalls blocking ICMP do not hide them; ARP does not cross routers. Tools: arp-scan, netdiscover. | RFC 826; Nmap reference guide "Host Discovery"; kali.org arp-scan, netdiscover | no |
| ICMP echo ping (`-PE`): type 8 request, type 0 reply = up; often blocked at perimeters. ICMP timestamp (`-PP`, type 13/14) and address mask (`-PM`, type 17/18) pings are alternatives when only echo is filtered. | RFC 792; RFC 950; Nmap reference guide "Host Discovery" (ICMP ping types) | no |
| TCP SYN ping (`-PS`, default port 80): SYN/ACK or RST back = host up (either reply proves a live host). TCP ACK ping (`-PA`): an unsolicited ACK gets a RST from a live host; useful against stateless filters that only block SYNs, but stateful firewalls drop it. | Nmap reference guide "Host Discovery"; RFC 9293 §3.10.7 | no |
| UDP ping (`-PU`, default port 40125): an ICMP port unreachable reply proves the host is up; an uncommon port is used so a closed-port error is likely. SCTP INIT ping (`-PY`) and IP protocol ping (`-PO`) are further options. | Nmap reference guide "Host Discovery"; RFC 1122 §4.1.3.1 | no |
| Ping sweep tools by name: fping (many hosts in parallel, script-friendly), Angry IP Scanner (GUI), Nmap `-sn`, hping3 ICMP mode (`-1`). | kali.org fping; fping.org; angryip.org; Nmap reference guide; kali.org hping3 | no |
| A host that gives no reply to ping is not proven down: firewalls drop probes. That is why `-Pn` exists and why discovery combines ICMP, TCP and UDP probes. | Nmap reference guide "Host Discovery"; Nmap book "Host Discovery" chapter | no |
| IPv6: the address space (a /64 per subnet) makes brute-force sweeps impractical; discovery relies on DNS, address patterns, on-link Neighbor Discovery and multicast (ff02::1). | RFC 7707 §3–4; RFC 4861 | no |
| EC-Council host-discovery technique names: ARP ping scan, UDP ping scan, ICMP ECHO ping scan, ICMP timestamp ping, ICMP address mask ping, TCP SYN ping, TCP ACK ping, IP protocol ping, ping sweep. | EC-Council CEH page (topic names); Nmap reference guide (same probes) | **yes** (EC names) |
| Defender view: many ARP requests or ICMP echo requests from one source across a range in seconds is a sweep signature; IDS rules and flow logs (Zeek conn.log) show one source touching many destinations. | NIST SP 800-94 §4 (network-based IDPS, reconnaissance detection); Zeek conn.log docs; Snort 3 port_scan notes (portsweep) | no |

## Port and Service Discovery

| Fact | Sources | verify |
|---|---|---|
| Nmap reports six port states: open, closed, filtered, unfiltered, open\|filtered, closed\|filtered. States describe how Nmap sees the port from where it scans, not a property of the port. | Nmap reference guide "Port Scanning Basics"; Nmap book "Port Scanning Overview" | no |
| Meaning: open = an application accepts connections/datagrams; closed = reachable but nothing listening; filtered = a filter blocks the probes so Nmap cannot tell; unfiltered = reachable, open/closed unknown (ACK scan only); open\|filtered = open or filtered, no way to tell (UDP, IP protocol, FIN, NULL, Xmas); closed\|filtered = only from the idle scan. | Nmap reference guide "Port Scanning Basics" | no |
| SYN scan (`-sS`, half-open, stealth): SYN/ACK → open (Nmap then sends RST), RST → closed, no reply after retransmission or ICMP unreachable type 3 code 0/1/2/3/9/10/13 → filtered. Default scan with raw-packet privileges. | Nmap reference guide "Port Scanning Techniques"; Nmap book "TCP SYN (Stealth) Scan" | no |
| Connect scan (`-sT`, full open): the OS `connect()` call completes the handshake; default for unprivileged users; more likely to be logged by the target application. | Nmap reference guide "Port Scanning Techniques"; Nmap book "TCP Connect Scan" | no |
| NULL (`-sN`, no flags), FIN (`-sF`, FIN), Xmas (`-sX`, FIN+PSH+URG): RST → closed; no reply → open\|filtered; ICMP unreachable → filtered. Relies on RFC 793 behaviour; Windows, many Cisco devices and some others send RST from every port, so every port looks closed. EC-Council calls these "inverse TCP flag" scans. | Nmap book "TCP FIN, NULL, and Xmas Scans"; RFC 9293 §3.10.7; EC-Council topic name | no (EC name: **yes**) |
| Maimon scan (`-sM`, FIN/ACK): RFC says RST from both open and closed ports, but many BSD systems drop it for open ports; RST → closed, no reply → open\|filtered. | Nmap book "TCP Maimon Scan"; Nmap reference guide | no |
| ACK scan (`-sA`): RST → unfiltered, no reply or ICMP error → filtered; never finds open ports; maps firewall rulesets (stateful or not). Window scan (`-sW`): like ACK, but reads the TCP window of the RST (positive → open, zero → closed) on some systems only. | Nmap book "TCP ACK Scan", "TCP Window Scan" | no |
| EC-Council "ACK flag probe scanning": attacker reads the TTL or window of RST replies to infer open ports on some old stacks (TTL-based and window-based analysis). | EC-Council framing; Nmap book "TCP Window Scan" (window idea only) | **yes** |
| UDP scan (`-sU`): UDP reply → open; no reply → open\|filtered; ICMP port unreachable (type 3 code 3) → closed; other ICMP unreachable (codes 0, 1, 2, 9, 10, 13) → filtered. Slow because silence is ambiguous and Linux rate-limits ICMP errors (about one per second by default). `-sV` helps separate open from filtered. | Nmap book "UDP Scan"; RFC 792; Linux ip-sysctl `icmp_ratelimit` | no |
| Idle scan (`-sI`): spoofed probes appear to come from a "zombie" host with a predictable (incrementing) IP ID; the scanner reads the zombie's IP ID before and after to infer open vs closed\|filtered; no probe carries the scanner's address. | Nmap book "TCP Idle Scan"; RFC 6864 (IP ID field) | no |
| Other scan types by name: IP protocol scan (`-sO`, which IP protocols are supported), SCTP INIT (`-sY`: INIT-ACK → open, ABORT → closed) and COOKIE ECHO (`-sZ`), FTP bounce (`-b`, abuses an FTP server's PORT command; mostly patched), list scan (`-sL`). | Nmap reference guide "Port Scanning Techniques"; RFC 9260 (SCTP INIT/INIT-ACK/ABORT) | no |
| Port selection: Nmap scans the 1,000 most common ports per protocol by default; `-p` picks ports, `-p-` all 65,535, `-F` the 100 most common. | Nmap reference guide "Port Specification and Scan Order"; Nmap "Brief options summary" | no |
| Normal output columns: PORT (number/protocol), STATE, SERVICE (from `nmap-services`, a guess by port number), plus VERSION with `-sV`; "Not shown: N closed ports" collapses the common state; `--reason` shows the reply that set each state. Formats: `-oN` normal, `-oX` XML, `-oG` grepable, `-oA` all three. | Nmap reference guide "Output"; Nmap book "Normal Output", "Grepable Output" | no |
| Service/version detection (`-sV`) sends probes from `nmap-service-probes` to open ports and matches replies to name the protocol, application, version, sometimes the OS; `--version-intensity` 0–9. `-A` = OS detection + version detection + default scripts + traceroute. NSE (`-sC` or `--script`) runs Lua scripts by category (default, safe, discovery, vuln, …). | Nmap reference guide "Service and Version Detection", "OS Detection", "NSE" | no |
| Banner grabbing: reading the greeting or header a service sends (SSH version string, SMTP 220 line, HTTP `Server:` header). Active = connect and read (Netcat, Telnet, Nmap `-sV`); passive = read banners from captured traffic or error pages without new probes. | NIST glossary "banner grabbing"; OWASP WSTG "Fingerprint Web Server"; kali.org netcat | no |
| Fast scanners by name: Masscan (asynchronous, whole-Internet ranges, Nmap-like options), ZMap (single-probe Internet-wide surveys), RustScan (finds open ports fast, then hands them to Nmap), Unicornscan (asynchronous TCP/UDP). | github.com/robertdavidgraham/masscan; zmap.io; kali.org rustscan, unicornscan | no |
| hping3 as a port scanner: SYN probes with `-S -p <port>`; SYN+ACK back = open, RST+ACK = closed; `--scan` (`-8`) mode walks a port range. | Kali hping3 page (man text); RFC 9293 | no |

## OS Discovery

| Fact | Sources | verify |
|---|---|---|
| OS fingerprinting identifies the target's operating system from how its TCP/IP stack behaves, because stacks fill optional or loosely specified fields differently. | Nmap book "Remote OS Detection" (intro and methods); Nmap reference guide "OS Detection" | no |
| Active fingerprinting (Nmap `-O`): a series of TCP, UDP and ICMP probes; tests include TCP ISN sampling, TCP options and their order, IP ID sampling, initial window size; the result is compared with `nmap-os-db`. It works best with at least one open and one closed TCP port. Output lines: Device type, Running, OS CPE, OS details, Network Distance; "Aggressive OS guesses" when no exact match (`--osscan-guess`). | Nmap reference guide "OS Detection"; Nmap book "TCP/IP Fingerprinting Methods", "Usage and Examples" | no |
| Passive fingerprinting: no probes; the tool reads traffic the host sends anyway (SYN packets, TTL, window size, TCP options, DF bit). p0f is the reference passive fingerprinter. Stealthier but less precise, and it needs traffic to observe. | lcamtuf.coredump.cx/p0f3; kali.org p0f; Netresec "Passive OS Fingerprinting" | no |
| Typical default initial TTLs: 64 for Linux and most Unix-like systems, 128 for Windows, 255 for many network devices (Cisco IOS) and Solaris. Observed TTL = initial TTL minus hops, so round up to the nearest default. | Linux ip-sysctl `ip_default_ttl` (64); Netresec "Passive OS Fingerprinting" table | **yes** (Windows/Cisco values from one secondary source) |
| EC-Council TTL/window table (for example Linux 64 / 5840, Windows 128 / 65,535 or 8,192, Cisco 255 / 4,128) is exam framing; window defaults change between OS versions. | EC-Council framing; Netresec table (similar values) | **yes** |
| Banner grabbing as OS discovery: service banners often name the OS or distribution (for example an SSH version string with "Ubuntu", an IIS `Server:` header implies Windows). | NIST glossary "banner grabbing"; OWASP WSTG "Fingerprint Web Server" | no |
| Nmap scripts can report the OS through a service, for example `smb-os-discovery` over SMB; version detection can also name the OS family in its "Service Info" line. | Nmap reference guide "NSE" (script categories); Nmap reference guide "Service and Version Detection" | no |
| IPv6 OS detection exists in Nmap (`-6 -O`), with its own probe set. | Nmap reference guide "OS Detection"; Nmap book "IPv6 fingerprinting" (osdetect chapter) | no |
| Defender view: OS detection probes are unusual packets (odd flag and option combinations, probes to closed ports, a UDP probe to a closed port) that IDS rules flag as fingerprinting; scrubbing or normalising traffic at the perimeter and banner changes make results less reliable. | Nmap book "Defenses Against Nmap" (detection, trickery); NIST SP 800-94 §4 | no |

## Scanning Beyond IDS and Firewall

Concept classes only: what each class is, what it tries to hide, and what a defender sees.

| Fact | Sources | verify |
|---|---|---|
| Packet fragmentation: the probe's TCP header is split across small IP fragments so a filter or IDS that does not reassemble cannot read the flags. Defence: reassemble before inspecting, drop tiny or overlapping fragments (RFC 1858). | Nmap reference guide "Firewall/IDS Evasion and Spoofing"; RFC 1858 | no |
| Decoys: real probes are mixed with probes that carry forged source addresses, so logs show many apparent scanners. The real source is still present, and replies must reach it. Defence: correlate by timing and TTL, look for the one source that also completes other traffic. | Nmap reference guide "Firewall/IDS Evasion and Spoofing"; Nmap book "Subverting Intrusion Detection Systems" | no |
| Source address spoofing: forged source IPs; the scanner cannot see replies unless it can sniff the path. Defence: ingress/egress filtering (BCP 38) drops packets whose source cannot come from that interface. | Nmap reference guide (`-S`); RFC 2827; NIST glossary "spoofing" | no |
| Idle (zombie) scan: the only probes seen by the target come from the zombie. Defence: IP ID randomisation or per-destination IDs on hosts (modern Linux, Windows), so they make poor zombies; ingress filtering; IDS rules for spoofed traffic. | Nmap book "TCP Idle Scan"; RFC 6864 §4 | no |
| Source port manipulation: probes sent from a trusted-looking port (53 DNS, 20 FTP data, 67 DHCP) to pass stateless rules that allow "replies" from those ports. Defence: stateful filtering; never allow traffic just because of its source port. | Nmap reference guide (`--source-port`); Nmap book "Firewall Subversion"; NIST SP 800-41 r1 §2.1 | no |
| Slow timing: probes spread over minutes or hours to stay under IDS thresholds (Nmap templates T0 paranoid, T1 sneaky). Defence: longer correlation windows, flow logs, SIEM aggregation across days. | Nmap reference guide "Timing and Performance"; Snort 3 port_scan notes (time windows, sense levels) | no |
| Randomising target and port order, adding random data to packets, crafting unusual packets with packet builders (hping3, Scapy, Colasoft Packet Builder), bad checksums (a reply means a device answered without checking), source routing, MAC address spoofing on the LAN, and proxies or anonymisers to hide the true origin are further classes EC-Council lists. | Nmap reference guide "Firewall/IDS Evasion and Spoofing"; kali.org hping3, scapy; colasoft.com packet builder; EC-Council topic names | **yes** (EC grouping) |
| Firewall behaviour a scanner reveals: an ACK scan separates stateless from stateful filters; ICMP administratively prohibited (type 3 code 13) reveals a filtering device; hping3 and Nmap are both used to test firewall rules. | Nmap book "TCP ACK Scan"; RFC 1812 via IANA ICMP codes; kali.org hping3 | no |
| Honeypot detection is a separate topic (M12); a scanner can meet tarpits and fake open ports set up by defenders to slow and log scans. | Nmap book "Defenses Against Nmap" (trickery); NIST glossary "honeypot" | no |

## Network Scanning Countermeasures

| Fact | Sources | verify |
|---|---|---|
| Reduce the attack surface first: disable unneeded services and close unused ports; each open port is an avenue for attack. ATT&CK M1042 (Disable or Remove Feature or Program). | NIST SP 800-123 §4 (remove unnecessary services); Nmap book "Proactive Scanning"; attack.mitre.org M1042 | no |
| Default-deny firewall policy: allow only the traffic the organisation needs, inbound and outbound; stateful inspection tracks connections so unsolicited ACK/FIN/Xmas probes are dropped. | NIST SP 800-41 r1 §2.1, §4.1; NIST glossary "stateful inspection", "packet filter" | no |
| Network segmentation limits what an internal scan (T1046) can reach. ATT&CK M1030; M1031 Network Intrusion Prevention blocks known scan patterns at the boundary. | attack.mitre.org T1046 (mitigations), M1030, M1031 | no |
| IDS/IPS scan detection: flag one source that hits many ports on one host (portscan) or one port on many hosts (portsweep), unusual flag combinations (NULL, FIN-only, Xmas), and many half-open connections. Snort 3 `port_scan` inspector counts these per time window; Suricata `threshold`/`detection_filter` rate-limits alerts per source; Zeek conn.log states (S0, REJ, RSTO…) show failed attempts. | Snort 3 port_scan dev notes; Suricata thresholding docs; Zeek conn.log docs; NIST SP 800-94 §4.3 | no |
| ATT&CK T1595 is mostly outside the defender's control: mitigation M1056 (Pre-compromise) says to minimise exposed data; detection relies on network traffic (DS0029), for example many connections from one source, and on the low-and-slow patterns. | attack.mitre.org T1595, M1056, DS0029 | no |
| Rate limiting: limit ICMP replies and new-connection rates per source at the firewall or host; slows sweeps and fast scanners. | Linux ip-sysctl `icmp_ratelimit`; NIST SP 800-41 r1 (firewall capabilities); Suricata thresholding (detection side) | no |
| ICMP filtering: block unneeded ICMP types inbound (echo, timestamp, address mask) and outbound unreachables that leak topology, but keep what the network needs (fragmentation needed for Path MTU Discovery; ICMPv6 Neighbor Discovery and Packet Too Big per RFC 4890). | RFC 4890 §4; RFC 792; NIST SP 800-41 r1 §3 | no |
| Banner suppression: Apache `ServerTokens Prod` and `ServerSignature Off`; nginx `server_tokens off`; change default SSH/SMTP greetings where supported.
