# Research: M5 Vulnerability Analysis

Scope: the three sections in `content/modules/m05/meta.json`. The public CEH v13 course page lists the module's
key topics (vulnerability classification, vulnerability scoring systems and databases, vulnerability-management
life cycle, vulnerability research, vulnerability scanning and analysis, vulnerability assessment tools,
vulnerability assessment reports, AI-powered vulnerability assessment tools) and three labs (vulnerability
research with scoring systems and databases, assessment with scanners, analysis with AI). That list is used for
scope only; all wording below is ours, from public primary sources.

Every fact was checked against at least two independent sources, or against the document that defines it (a
specification is the authority on its own content). **verify** marks EC-Council-specific lists and framing
(their naming can differ from public frameworks) and facts backed by a single source.

Checked on 2026-09-23. URLs tested with curl and a browser User-Agent: all 200 except ISO (403, bot protection)
and SourceForge (403). JavaScript-only pages (cve.org, nvd.nist.gov) were read in a browser. Removed after a 404:
NIST glossary "exploit", "authenticated scan", "credentialed scan", "proof of concept", "end of life";
several old Tenable doc paths (CredentialedChecks, NessusAgents, Reports, SeverityAndVPR); FIRST "epss/model".

## Vulnerability Assessment Concepts

| Fact | Sources | verify |
|---|---|---|
| Vulnerability = weakness in a system, its security procedures, internal controls or implementation that a threat source could exploit. Risk combines the likelihood of a threat exploiting it and the impact. | NIST glossary "vulnerability", "risk"; NIST SP 800-30 Rev. 1 | no |
| Vulnerability assessment = systematic examination to find security deficiencies and confirm the adequacy of controls; it does not exploit (that is a penetration test). | NIST glossary "vulnerability assessment", "penetration testing"; NIST SP 800-115 | no |
| Common vulnerability classes: misconfiguration (OWASP A05:2021), default or hard-coded credentials (CWE-1392, CWE-798), weak password requirements (CWE-521), missing authentication (CWE-306), buffer overflows (CWE-120, CWE-787), outdated or vulnerable third-party components (OWASP A06:2021, CWE-1104, CWE-1395), zero-days. | CWE definitions; OWASP Top 10 2021 A05 and A06; NIST glossary "misconfiguration", "buffer overflow", "zero day attack" | no |
| EC-Council's classification list (misconfigurations, default installations, buffer overflows, OS flaws, application flaws, open services, default passwords, design flaws, zero-days, legacy platforms, third-party risks, patch management issues) is their own grouping. | EC-Council course page (topic "Vulnerability Classification"); public CWE/OWASP categories for the content | **yes** |
| CVE = catalog of publicly disclosed vulnerabilities; each CVE ID identifies one vulnerability. CVE IDs match `CVE-YYYY-NNNN…` (4 to 19 digits after the year). CNAs assign IDs and publish records; record states Reserved → Published, or Rejected. | cve.org Overview, FAQs, Glossary; CVE JSON schema (`^CVE-[0-9]{4}-[0-9]{4,19}$`) | no |
| The CVE Program is sponsored by CISA; MITRE operates it (Secretariat, Top-Level Root, CNA of Last Resort). | cve.org FAQs; CISA KEV page ("CVE Program is sponsored by CISA") | no |
| NVD (NIST) enriches CVE records with CVSS base scores, CWE and CPE applicability; it provides base metrics only (no temporal/threat/environmental). It stopped producing CVSS v2 scores for new CVEs on 2022-07-13. | nvd.nist.gov/vuln-metrics/cvss; nvd.nist.gov/general | no |
| CWE = list of weakness types (root-cause categories) in software and hardware; CVE = a specific vulnerability instance in a product; CAPEC = attack patterns that exploit weaknesses. | cwe.mitre.org About; capec.mitre.org About; cve.org Overview | no |
| CPE = standard naming scheme for IT products and platforms, used to say which products a CVE affects. | NVD CPE page; NIST glossary "common platform enumeration"; Greenbone glossary | no |
| CVSS is maintained by FIRST; scores 0–10 with a vector string. "CVSS is not a measure of risk" (NVD). v3.1 groups: Base, Temporal, Environmental. v4.0 groups: Base, Threat, Environmental, Supplemental. | FIRST CVSS v3.1 and v4.0 specifications; NVD CVSS page | no |
| CVSS v3.1 base metrics: AV (N/A/L/P), AC (L/H), PR (N/L/H), UI (N/R), S (U/C), C/I/A (H/L/N). Temporal: E, RL, RC. Environmental: CR/IR/AR and modified base metrics. | FIRST CVSS v3.1 specification; NVD v3.1 calculator | no |
| Severity: None 0.0, Low 0.1–3.9, Medium 4.0–6.9, High 7.0–8.9, Critical 9.0–10.0 (v3.x and v4.0). CVSS v2 (NVD): Low 0–3.9, Medium 4–6.9, High 7–10, no Critical. | FIRST v3.1 and v4.0 specifications; NVD CVSS page | no |
| Worked scores (v3.1): AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H = 9.8; same with S:C = 10.0; AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N = 6.1; AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H = 7.8; AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H = 7.5. | FIRST v3.1 equations (computed in `SCRATCH/m05/cvss31.py`); FIRST v3.1 calculator | no |
| CVSS v4.0 (Nov 2023): adds Attack Requirements (AT: N/P); UI becomes N/P/A (None, Passive, Active); Scope removed, impacts split into Vulnerable System (VC/VI/VA) and Subsequent System (SC/SI/SA); Threat group has only Exploit Maturity (E: A/P/U); nomenclature CVSS-B, CVSS-BT, CVSS-BE, CVSS-BTE; Supplemental metrics (Safety, Automatable, Recovery, Value Density, Vulnerability Response Effort, Provider Urgency) do not change the score. | FIRST CVSS v4.0 specification and FAQ; NVD CVSS page | no |
| EPSS (FIRST): daily probability (0–1) that a published CVE will be exploited in the wild in the next 30 days, plus a percentile rank; a machine-learning model (gradient-boosted trees); not a complete risk score. | first.org/epss; EPSS FAQ; EPSS "How it works" | no |
| CISA KEV catalog: vulnerabilities exploited in the wild. Entry criteria: assigned CVE ID, reliable evidence of active exploitation, clear remediation action. BOD 22-01 requires federal civilian agencies to remediate by the due date (default 6 months for CVEs from before 2021, two weeks for others). | CISA KEV page; BOD 22-01 | no |
| SSVC (CISA): decision tree with outcomes Track, Track*, Attend, Act. | CISA SSVC page; CISA KEV page (prioritization inputs) | no |
| NIST SP 800-40 Rev. 4 vulnerability management life cycle: know about new vulnerabilities (inventory + feeds), plan the risk response, execute it (prepare, implement, verify, continuously monitor). Risk responses: accept, mitigate, transfer, avoid. Patching is the only response that removes the vulnerability. | NIST SP 800-40 Rev. 4 §2.1–2.2 (landing page and PDF); NIST SP 800-30 Rev. 1 | no |
| EC-Council's vulnerability-management life cycle: pre-assessment (identify assets, create a baseline) → vulnerability assessment (scan) → post-assessment (risk assessment, remediation, verification, monitoring). | EC-Council course page (topic name only); maps to NIST SP 800-40 Rev. 4 life cycle | **yes** |
| Vulnerability research (EC framing): studying products, protocols and configurations to find flaws before attackers do, classifying by severity and by exploit range (local or remote). Public resources: CVE, NVD, CWE, Exploit-DB, vendor advisories, KEV. | EC-Council course page (topic "Vulnerability Research"); cve.org; NVD; Exploit-DB | **yes** |
| Assessment types: active vs passive, external vs internal, host-based vs network-based, application, database, wireless, credentialed vs non-credentialed, manual vs automated. Internal scanning usually finds more than external; credentialed scans read patch levels directly. | NIST SP 800-115 §4.3; Tenable Nessus credentials docs; EC-Council course page (grouping) | **yes** (EC grouping) |
| Assessment approaches (EC framing): product-based vs service-based solutions; tree-based vs inference-based assessment. | EC-Council framing only | **yes** |
| Coordinated vulnerability disclosure: the finder reports privately to the vendor/CNA, a fix and advisory are prepared, then details go public. | CISA CVD process; ISO/IEC 29147; OWASP Vulnerability Disclosure Cheat Sheet | no |

## Vulnerability Assessment Tools

| Fact | Sources | verify |
|---|---|---|
| A vulnerability scanner identifies hosts, OS and applications, then matches them with a database of known vulnerabilities; it finds outdated software, missing patches and misconfigurations. Scanners can have high false positive rates and generate much more traffic than a port scan. | NIST SP 800-115 §4.3; NIST glossary "vulnerability scanning" | no |
| Credentialed (authenticated) scans log in and check installed versions and settings; network-based unauthenticated scans rely on banners and remote probes. Nessus stops trying other credentials once one works. | NIST SP 800-115 §4.3; Tenable Nessus "Credentials" docs | no |
| Agent-based scanning: a local agent collects data and reports to a manager; low network impact, good for laptops that leave the network. | Tenable Nessus "Agents" docs; NIST glossary "agent" | no |
| Passive vulnerability detection: listening to traffic from a SPAN port or tap (Tenable Network Monitor) instead of sending probes; avoids disruption but sees only what crosses the wire. | Tenable Network Monitor docs; Tenable NNM product page | no |
| Nessus: web UI on TCP 8834; plugins (written in NASL) per check; templates such as Host Discovery, Basic Network Scan, Advanced Scan, Credentialed Patch Audit; severity Critical/High/Medium/Low/Info from CVSS; Tenable VPR (0.1–10) adds threat data. Nessus Essentials is a free, limited edition (IP limit changes over time). | Tenable docs: Port Requirements, Scan and Policy Templates, Plugins, Risk Metrics; Nessus Essentials page | no |
| Greenbone / OpenVAS: gvmd (manager) controls the OpenVAS scanner through OSP (ospd-openvas); GSA web UI (Kali: https://127.0.0.1:9392, set up with `gvm-setup`, checked with `gvm-check-setup`); Vulnerability Tests (NVTs) are NASL scripts from the Greenbone Community Feed. | Greenbone docs (architecture, glossary, Kali install); Kali gvm tool page | no |
| Greenbone Quality of Detection (QoD): 0–100 % reliability of a detection; by default only results with QoD ≥ 70 % are shown. | Greenbone GSM manual (reports, scanning); Greenbone docs | no |
| Nikto: open-source web server scanner; checks dangerous files/programs, outdated server versions and misconfigurations. Options: `-h` host, `-port`, `-ssl`, `-Tuning` (test classes), `-evasion` (URI encoding tricks), `-o`/`-Format` (csv, json, htm, txt, xml). It is noisy (thousands of requests visible in web logs). | cirt.net Nikto2; Kali nikto page; github.com/sullo/nikto | no |
| Nmap NSE `vuln` category scripts check for specific known vulnerabilities; `vulners` maps detected CPEs (needs `-sV`) to CVEs with CVSS scores. | nmap.org NSE vuln category; vulners script page; Nmap NSE usage | no |
| Nuclei: template-based scanner (YAML templates) for web apps, APIs, networks, DNS and cloud configurations. | github.com/projectdiscovery/nuclei; ProjectDiscovery docs | no |
| OWASP ZAP: passive scan inspects requests/responses without changing them; active scan sends attacks and must be run only on apps you are allowed to test. | ZAP docs (passive scan, active scan); OWASP Vulnerability Scanning Tools | no |
| Other classes: SCA / dependency scanners (OWASP Dependency-Check, Trivy for images, filesystems, repos, Kubernetes), host audit (Lynis on Linux/macOS/Unix), cloud VM platforms (Qualys VMDR), exploit lookups (Exploit-DB / `searchsploit`). | Tool pages (OWASP Dependency-Check, Trivy, Lynis/CISOfy, Qualys, Kali exploitdb) | no |
| EC-Council's grouping of VA tool types (host-based, depth assessment, application-layer, scope assessment, active/passive, location and data examination: network-based, agent-based, proxy, cluster scanners) and its criteria for choosing a tool. | EC-Council framing only | **yes** |
| AI-powered vulnerability assessment: ML ranking (EPSS gradient-boosted model; vendor scores such as Tenable VPR), LLM assistants (for example ShellGPT) that draft scan commands or summarize results. Outputs must be verified; client scan data must not go to public AI services; LLM apps are themselves scan targets (OWASP LLM Top 10). | EPSS "How it works"; Tenable Risk Metrics; ShellGPT repo; OWASP Top 10 for LLM Applications; EC-Council course page (topic name) | **yes** (EC tool list may differ) |

## Vulnerability Assessment Reports

| Fact | Sources | verify |
|---|---|---|
| After analysis, a report identifies system, network and organizational vulnerabilities and recommended mitigations; audiences differ (CIO/CISO vs technical staff), so several formats may be needed. Internal reports include methodology, results, analysis and a POA&M. | NIST SP 800-115 §8.2; NIST glossary "plan of action and milestones" | no |
| Mitigation recommendations should include root-cause analysis and both technical (apply a patch) and non-technical (fix the patch process) fixes. | NIST SP 800-115 §8.1; NIST glossary "root cause analysis" | no |
| Remediation process: test the fix on a comparable system first, coordinate through configuration/change management, then deploy, then verify. | NIST SP 800-115 §8.3; NIST SP 800-40 Rev. 4 §2.3 | no |
| False positive = reported but not present; false negative = present but missed. Validate before reporting; scanners suffer from both. | NIST glossary "false positive", "false negative"; NIST SP 800-115 §4.3 | no |
| Prioritize by more than CVSS base: exploitation evidence (KEV), exploitation probability (EPSS), asset value and exposure (CVSS environmental metrics / SSVC). | CISA KEV; FIRST EPSS FAQ; CISA SSVC; CVSS v3.1 user guide (base score is not risk) | no |
| Typical scanner report parts (host list, findings by severity, plugin/NVT output, CVE/CVSS references, solution) and export formats (Nessus: .nessus, CSV, HTML, PDF; Greenbone report formats). | Tenable "Export a Scan" docs; Greenbone GSM manual reports chapter | no |
| EC-Council's report structure: executive summary, assessment overview (scope, methodology, tools), findings (scanned hosts, vulnerabilities, CVE, severity), risk assessment, recommendations. | EC-Council framing; overlaps NIST SP 800-115 §8 | **yes** |
| Risk responses to a finding: accept (document), mitigate (patch, compensating control), transfer, avoid (remove the software). Compensating control = alternative control providing comparable protection. | NIST SP 800-40 Rev. 4 §2.1; NIST glossary "compensating controls" | no |
| Rescanning verifies remediation; Nessus VPR is static inside Nessus until you rescan. | NIST SP 800-40 Rev. 4 (verify step); Tenable Risk Metrics docs | no |
| Scan reports are sensitive (a map of weaknesses): restrict and encrypt them. | NIST SP 800-115 §7.4 (data handling: architecture, configurations and vulnerabilities are sensitive); NCSC vulnerability management guidance | **yes** (single primary source) |
