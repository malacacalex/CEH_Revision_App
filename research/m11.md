key topics (session hijacking, application-level session hijacking, compromising session IDs, network-level
session hijacking, TCP/IP hijacking, RST hijacking, blind hijacking, session hijacking tools, detection methods

session hijacking). That list is used for scope only; all wording below is ours, from public primary sources.

## Session Hijacking Concepts

| Fact | Sources | verify |
|---|---|---|
| HTTP is stateless; after login the server gives the client a session token (usually a cookie, sometimes a URL parameter, hidden field or header) and treats whoever presents it as that user. | OWASP "Session hijacking attack"; OWASP SM CS (introduction, exchange mechanisms) | no |
| Session hijacking = stealing or predicting a valid session token to act as the user without their credentials. | OWASP "Session hijacking attack"; NIST glossary "session hijack attack"; WSTG-SESS-09 | no |
| Ways tokens are compromised: predictable tokens, session sniffing, client-side attacks (XSS, malicious JavaScript, trojans), man-in-the-middle, man-in-the-browser. | OWASP "Session hijacking attack"; MITRE ATT&CK T1539 | no |
| A stolen session cookie lets the attacker skip the password and MFA because the session is already authenticated (MITRE T1550.004 "Web Session Cookie"). | MITRE ATT&CK T1539; MITRE ATT&CK T1550.004 | no |
| ATT&CK mapping: T1539 Steal Web Session Cookie (Credential Access); T1185 Browser Session Hijacking (Collection, browser pivoting/injection); T1563 Remote Service Session Hijacking (Lateral Movement) with sub-techniques .001 SSH and .002 RDP; T1550.004 use of a stolen web session cookie. | MITRE ATT&CK T1539, T1185, T1563, T1563.001, T1563.002, T1550.004 | no |
| Hijacking takes over a session that already exists; spoofing starts a new session by pretending to be someone else. MITRE makes the same distinction for T1563 (hijacks an existing session, unlike Remote Services with valid accounts). | MITRE ATT&CK T1563; OWASP "Session hijacking attack" | no (the "spoofing vs hijacking" contrast as a list item is EC-Council framing: tag `ec-council-specific`) |
| Passive hijacking = watch and record the session traffic; active hijacking = take over the session and act in it (often knocking the user off). | EC-Council course page (topic names); MITRE T1040 (sniffing) vs T1563 (takeover) | **yes** (`ec-council-specific`) |
| Two levels: application level (steal/predict/fix the HTTP session token) and network level (take over the TCP or UDP flow itself). | EC-Council course page (key topics); OWASP "Session hijacking attack" and RFC 5961 (network-level injection) | **yes** for the two-level split as a list (`ec-council-specific`) |
| Generic network hijack flow taught by EC-Council: sniff → monitor → desynchronize the session → predict sequence numbers → inject / take over. | EC-Council course page (topic "TCP/IP Hijacking"); RFC 5961 (in-window guessing) | **yes** (`ec-council-specific`) |
| Why hijacking works: no or weak encryption (tokens in cleartext), predictable IDs, no timeout, IDs in URLs, no ID renewal on login, long-lived sessions, missing cookie flags. | OWASP SM CS; WSTG-SESS-04 (exposed session variables) | no |
| Session fixation is not strictly a theft of an existing post-login session: the attacker fixes the ID before the login. | OWASP "Session fixation"; WSTG-SESS-03 | no |
| Remote-service hijacking: SSH agent socket/agent forwarding abuse (T1563.001), RDP session takeover with `tscon` under SYSTEM (T1563.002). | MITRE T1563.001, T1563.002; Microsoft `tscon` command reference | no |

## Application-Level Session Hijacking

| Fact | Sources | verify |
|---|---|---|
| Session fixation: attacker obtains or sets a valid session ID, makes the victim use it (URL parameter, hidden field, injected cookie, meta tag, Set-Cookie injection), victim logs in, the app keeps the same ID, attacker reuses it. | OWASP "Session fixation"; WSTG-SESS-03; CWE-384 | no |
| Fix for fixation: issue a new session ID at authentication (and every privilege change); reject IDs the server did not issue ("strict" vs "permissive" session management). | OWASP SM CS (renew ID, permissive vs strict); WSTG-SESS-03; CWE-384 | no |
| Session prediction: the attacker guesses valid IDs because they are sequential, time-based or low-entropy. Needs a CSPRNG and ≥ 64 bits of entropy. | OWASP "Session Prediction"; OWASP SM CS (entropy ≥ 64 bits, CSPRNG); CWE-330/331 | no |
| NIST: session secrets come from an approved random bit generator, are at least 64 bits long, and are created at or just after authentication. | NIST 800-63B-4 session binding requirements; OWASP SM CS | no |
| Session ID content must be meaningless (no user data); default names (PHPSESSID, JSESSIONID, ASP.NET_SessionId) fingerprint the framework, so rename to a generic name. | OWASP SM CS (name fingerprinting, content) ; WSTG-SESS-01 | no |
| Cookie theft via XSS: injected script reads `document.cookie` and sends it out; HttpOnly blocks script access to the cookie (does not fix the XSS). | OWASP "Session hijacking attack" (XSS example); OWASP HttpOnly; RFC 6265 §4.1.2.6; OWASP XSS Prevention CS | no |
| HttpOnly does not stop an XSS payload from making requests in the victim's browser (the browser still attaches the cookie). | OWASP SM CS (HttpOnly attribute); OWASP HttpOnly page | no |
| Session sniffing / sidejacking: session cookie captured from unencrypted HTTP traffic and replayed; Kali packages ferret (extracts data from traffic) and hamster (proxy that swaps in captured cookies) implement it. | Kali tools ferret-sidejack and hamster-sidejack; WSTG-SESS-09 | no |
| Session IDs in URLs leak through browser history, logs, and the Referer header; prefer cookies. | OWASP SM CS (exchange mechanisms); CWE-598; WSTG-SESS-04 | no |
| Man-in-the-browser: malware (typically a banking trojan/browser extension) modifies pages and transactions inside the browser; TLS does not help because the attack is at the endpoint. MITRE T1185 covers browser pivoting/injection. | OWASP "Man-in-the-browser attack"; MITRE T1185 | no |
| CSRF rides the victim's existing session (browser auto-sends cookies) without stealing the token; defenses: anti-CSRF tokens, SameSite cookies. | OWASP CSRF; OWASP CSRF Prevention CS; CWE-352 | no |
| CRIME (CVE-2012-4929) recovers secrets such as cookies when TLS-level compression is on; BREACH does the same with HTTP body compression. Fix: disable TLS compression (TLS 1.3 removed it). | RFC 7457 §2.6; breachattack.com; RFC 8446 | no |
| "Forbidden attack": reuse of an AES-GCM nonce with the same key breaks confidentiality and authenticity, letting an attacker forge TLS records. | RFC 5116 (nonce reuse consequences); NIST SP 800-38D | **yes** (EC-Council name, `ec-council-specific`) |
| Session replay: capture a valid token or authenticated message and resend it; defenses are timeouts, one-time tokens/nonces and TLS. | NIST glossary "replay attack"; CWE-294 | no |
| Session puzzling (session variable overloading): the same session variable is used for more than one purpose, so an attacker sets it through one flow (e.g. password reset) and reuses it in another. | WSTG-SESS-08 | **yes** (single source) |
| Adversary-in-the-middle phishing proxies (e.g. Evilginx2 per MITRE) capture session cookies after the user completes MFA. | MITRE T1539; MITRE T1557 | no |
| Burp Sequencer analyzes the randomness of a token sample (session tokens, anti-CSRF tokens, reset tokens). | PortSwigger Burp Sequencer docs; WSTG-SESS-01 (token randomness analysis) | no |
| OWASP ZAP passive alerts: 10010 Cookie No HttpOnly Flag (CWE-1004), 10011 Cookie Without Secure Flag (CWE-614), 10054 Cookie without SameSite; active rule 40013 Session Fixation. | ZAP alert pages 10010, 10011, 10054, 40013; CWE-1004/614 | no |
| Hetty (open-source HTTP toolkit, MITM proxy) and Caido (web security auditing toolkit) are proxy tools that appear in EC-Council's hijacking labs. | Hetty GitHub; Caido docs; EC-Council course page (labs listed by name only) | **yes** (lab tool list is `ec-council-specific`) |

## Network-Level Session Hijacking

| Fact | Sources | verify |
|---|---|---|
| TCP accepts a segment only if its sequence number falls in the receiver's window; sequence and acknowledgment numbers are 32-bit fields. Taking over a TCP session means sending segments with the right 4-tuple and in-window numbers. | RFC 9293 (header, segment acceptability); RFC 5961 abstract | no |
| Blind hijacking: the attacker cannot see replies, so must guess the ISN/sequence numbers; randomized ISNs make this impractical. | RFC 6528; RFC 5961 §5 (blind data injection) | no |
| RFC 6528 ISN = M + F(localip, localport, remoteip, remoteport, secretkey), M a 4 µs timer, F a keyed PRF (hash) not computable from outside. It replaced RFC 1948. | RFC 6528; RFC 1948 | no |
| RST hijacking / blind reset: a forged RST with an in-window sequence number tears down the connection; RFC 5961 adds challenge ACKs (exact sequence match needed) for RST, SYN and data injection. | RFC 5961 §3-5; RFC 4953; RFC 9293 (reset processing) | no |
| Desynchronization/ACK storm: after injected data the real client and server disagree on sequence numbers and bounce ACKs; RFC 5961 notes RST/ACK "wars". | RFC 5961 (RST/ACK war note); EC-Council framing ("ACK storm") | **yes** |
| UDP hijacking: UDP has no handshake or sequence numbers, so the attacker races the real server with a forged reply (DNS is the classic case: RFC 5452 randomizes source port and ID). | RFC 768; RFC 5452 | no |
| MITM via ARP spoofing: forged ARP replies map the gateway's IP to the attacker's MAC (T1557.002); detection with arpwatch (IP/MAC pair database, alerts on changes) and prevention with dynamic ARP inspection / static entries. | MITRE T1557.002; RFC 826; Kali arpwatch page; Cisco DAI guide | no |
| MITM via forged ICMP redirect: a fake redirect tells a host to route via the attacker; hosts should not accept redirects (Linux `accept_redirects` = 0). | RFC 792; Linux kernel ip-sysctl docs | no |
| IP source routing (LSRR/SSRR) lets a spoofing attacker get replies routed back through them; RFC 7126 says the default for LSRR/SSRR packets should be drop; IPv6 RH0 was deprecated. | RFC 7126 §4.3–4.4; RFC 5095 | no |
| IP spoofing defenses: ingress/egress filtering (BCP 38 / RFC 2827). | RFC 2827; RFC 4953 | no |
| Ettercap: sniffer/interceptor for switched LANs that supports data injection into an established connection while keeping it synchronized; bettercap: modular MITM/sniffing framework. | Kali ettercap page; ettercap-project.org; Kali bettercap page; bettercap.org | no |
| sslstrip rewrites HTTPS links and redirects into HTTP on a MITM position; HSTS is the defense. | Kali sslstrip page; RFC 7457 §2.1; RFC 6797 | no |
| Wireshark TCP analysis flags such as "ACKed unseen segment", retransmissions and duplicate ACKs help spot injected or desynchronized flows. | Wireshark User's Guide (TCP analysis); Wireshark wiki | **yes** (use as detection clue is our framing) |

## Session Hijacking Countermeasures

| Fact | Sources | verify |
|---|---|---|
| Cookie attributes (RFC 6265): Secure (send only over secure channels), HttpOnly (hide from non-HTTP APIs such as scripts), Domain, Path, Expires/Max-Age. SameSite comes from RFC 6265bis and browsers. | RFC 6265 §4.1.2, §5.2; MDN Set-Cookie; RFC 6265bis draft | no |
| SameSite=Strict omits the cookie on all cross-site requests; Lax allows top-level safe navigations; None requires Secure. It is defense in depth against CSRF, not a replacement for tokens. | OWASP SM CS (SameSite); MDN Set-Cookie; OWASP CSRF Prevention CS | no |
| `__Host-` prefix: cookie must be Secure, set from HTTPS, no Domain, Path=/ (recommended for session IDs); `__Secure-` only needs Secure. | OWASP SM CS (cookie prefixes); MDN Set-Cookie | no |
| Session (non-persistent) cookies: no Expires/Max-Age, so they are not written to disk; Max-Age wins over Expires. | OWASP SM CS (Expire and Max-Age); RFC 6265 §5.3 | no |
| Timeouts: idle 2–5 min for high-value apps, 15–30 min for low risk; absolute 4–8 h for an office-day app; invalidate on the server at expiry and logout. | OWASP SM CS (timeouts, manual expiration); WSTG-SESS-07 | no |
| NIST 800-63B-4: AAL2 overall ≤ 24 h, inactivity ≤ 1 h; AAL3 overall ≤ 12 h, inactivity ≤ 15 min; session cookies SHALL be secure-only and SHOULD be HttpOnly. | NIST 800-63B-4; OWASP SM CS | no |
| Renew the session ID after login and any privilege change (password change, role switch). | OWASP SM CS; WSTG-SESS-03; CWE-384 | no |
| Binding the session to client properties (IP, User-Agent, client certificate) helps detect hijacking; changes mid-session are an indicator. | OWASP SM CS (binding) ; MITRE T1539 M1047 (impossible travel, anomalous session use) | no |
| Reauthenticate for risky events (password change, new device/IP, sensitive actions). | OWASP SM CS (reauthentication after risk events); NIST 800-63B-4 (reauthentication) | no |
| HSTS (RFC 6797): `Strict-Transport-Security: max-age=…; includeSubDomains`; header only honored over HTTPS; first visit is exposed (bootstrap MITM), fixed by the browser preload list, which needs max-age ≥ 1 year and includeSubDomains; `max-age=0` removes the policy. | RFC 6797; MDN Strict-Transport-Security; hstspreload.org | no |
| Full HSTS (with includeSubDomains) is needed when session cookies use the Domain attribute, otherwise a non-HSTS subdomain can leak or inject them. | WSTG-SESS-09; WSTG-SESS-03 | no |
| HPKP is obsolete; do not recommend it. | MDN HPKP glossary; RFC 7469 | no |
| Network-level: encrypt the whole channel (TLS, SSH instead of Telnet, IPsec; ESP gives confidentiality, AH integrity and origin authentication), randomized ISNs (RFC 6528), RFC 5961 checks, anti-spoofing filters, DAI. | RFC 4301/4302/4303; NIST SP 800-77r1; RFC 6528; RFC 5961 | no |
| MITRE mitigations: T1539 audit (impossible travel), MFA with hardware keys; T1563 disable unneeded remote services, segment networks; T1563.001 disable SSH agent forwarding; T1550.004 delete persistent cookies. | MITRE T1539, T1563, T1563.001, T1550.004 | no |
| Detection: IDS/IPS rules (Snort/Suricata), Wireshark analysis, arpwatch, session anomaly logging; the EC-Council list of "detection methods" is manual vs automatic. | Snort docs; Suricata docs; OWASP SM CS (logging session life cycle) | **yes** for the manual/automatic split (`ec-council-specific`) |
| Device-bound session credentials (Chrome DBSC) and token binding (RFC 8471) tie a session to a key on the device so a copied cookie is useless elsewhere. | Chrome DBSC docs; RFC 8471 | **yes** (emerging, browser-specific) |
| Web Storage (localStorage) is readable by any script on the origin, so it is a poor place for session tokens. | OWASP SM CS (HTML5 Web Storage); OWASP HTML5 guidance (same cheat sheet) | **yes** (single source family) |
