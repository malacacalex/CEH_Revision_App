## IDS, IPS, and Firewall Concepts

| Fact | Sources | verify |
|---|---|---|
| Firewall = a gateway that limits access between networks per a security policy. | NIST glossary "firewall" (SP 800-12 Rev. 1); NIST SP 800-41 Rev. 1 | no |
| IDS = software/service that automates intrusion detection (monitors and analyzes events for signs of attack); IPS adds the ability to attempt to stop the attack before it reaches its target. | NIST glossary "intrusion detection system" and "intrusion prevention system"; NIST SP 800-94 §2 | no |
| The only functional difference between IDS and IPS is response: an IPS can terminate the connection/session, block the source, block the target, or alter the attack's content (e.g. drop the malicious packet, strip a bad attachment). | NIST SP 800-94 §2.1 (IPS response groups); IBM "intrusion detection system" | no |
| Three detection methodologies: signature-based (matches known patterns), anomaly-based (compares to a normal baseline profile), stateful protocol analysis (compares to vendor profiles of benign protocol state). | NIST SP 800-94 §2.3 | no |
| Signature-based: effective on known threats, simple, but blind to unknown/zero-day attacks and to variants; anomaly-based: catches unknown threats but produces many false positives and needs a training period. | NIST SP 800-94 §2.3.1–2.3.2 | no |
| False positive = benign activity flagged as malicious; false negative = malicious activity missed. Reducing one usually increases the other; adjusting the IDPS to improve accuracy is called tuning. | NIST SP 800-94 §2.1; NIST glossary "false positive"/"false negative" | no |
| Four IDPS technology types by what they monitor: network-based (NIDS), wireless, network behavior analysis (NBA), host-based (HIDS). | NIST SP 800-94 §2.4 | no |
| HIDS monitors one host: system logs, running processes, file access and integrity, config changes, and (only for that host) network traffic. | NIST SP 800-94 §7.2.2 | no |
| NIDS can be deployed inline (traffic passes through it, so it can block) or passive (monitors a copy via SPAN/mirror port, network tap, or IDS load balancer; cannot block reliably). | NIST SP 800-94 §4.2 | no |
| A network IDS/IPS cannot inspect attacks inside encrypted traffic (VPN/TLS/SSH); place sensors where traffic is unencrypted, or use host-based agents that see the decrypted activity. | NIST SP 800-94 §4.3.5; NIST SP 800-41 Rev. 1 §2.3 | no |
| A network IDS is inherently "fail-open": if disabled by a DoS it stops protecting, unlike a fail-closed firewall. | Ptacek & Newsham, "Insertion, Evasion, and Denial of Service" (1998) §2.2 | no |
| Thresholds, blacklists and whitelists are common IDPS tuning tools; a threshold sets the limit between normal and abnormal (e.g. x failed logins in 60 s). | NIST SP 800-94 §3.2 | no |

## IDS, IPS, and Firewall Solutions

| Fact | Sources | verify |
|---|---|---|
| Packet filter (stateless): a routing device with an ACL ruleset that judges each packet alone on source/dest IP, protocol, and port; no connection state, so it cannot relate packets in a session. | NIST SP 800-41 Rev. 1 §2.1.1; NIST glossary "packet filter" | no |
| Stateful inspection: tracks each connection in a state table (src/dst IP, ports, connection state) and blocks packets that deviate from the expected TCP state. | NIST SP 800-41 Rev. 1 §2.1.2; NIST glossary "stateful inspection" | no |
| Application/proxy-gateway firewall: a proxy agent terminates the connection and opens a second one to the destination, so the two hosts never connect directly; it inspects application-layer content and hides internal IPs. | NIST SP 800-41 Rev. 1 §2.1.4; NIST glossary "application proxy gateway" | no |
| Circuit-level gateway: works at the OSI session layer, sets up two TCP/UDP connections and relays approved sessions (e.g. SOCKS) without inspecting payload content. | Palo Alto Networks "circuit-level gateway"; RFC 1928 (SOCKS v5) | no |
| Stateful protocol analysis / deep packet inspection (DPI) adds basic IDS to stateful inspection: an engine checks application-layer protocol behavior against vendor profiles. | NIST SP 800-41 Rev. 1 §2.1.3; NIST glossary "stateful protocol analysis" | no |
| Next-generation firewall (NGFW) = stateful firewall plus application awareness (app-ID), integrated IPS, and deep packet inspection, often with TLS inspection and threat intelligence. | Palo Alto Networks "what is a NGFW"; Fortinet "next-generation firewall" | no |
| Unified threat management (UTM) merges firewall, malware detection, IDS/IPS and more into one appliance; simpler to manage but one box must have the resources for every task. | NIST SP 800-41 Rev. 1 §2.1.8 | no |
| Web application firewall (WAF) sits in front of a web server and applies rules to HTTP to block web attacks (XSS, SQLi); protects the server, unlike a proxy that protects clients. | NIST SP 800-41 Rev. 1 §2.1.9; OWASP "Web Application Firewall" | no |
| DMZ (screened subnet): a perimeter segment logically between the internal and external networks; public-facing servers (web, mail) go here so external traffic never reaches the internal LAN directly. | NIST SP 800-41 Rev. 1 §3.1; NIST glossary "demilitarized zone" | no |
| A bastion host is a hardened, single-purpose host built to withstand attack, typically exposed in the DMZ. | NIST glossary "bastion host" (CNSSI 4009) | no |
| Firewalls should be deny-by-default: block everything not explicitly permitted; put the most-matched rules near the top for firewalls that match rules sequentially. | NIST SP 800-41 Rev. 1 §2.4, executive summary, §4.1 | no |
| NAT is a routing technology, not a security feature; its "protection" (hiding internal hosts) can be matched by a stateful firewall. | NIST SP 800-41 Rev. 1 §3.2; NIST glossary "network address translation" | no |
| Snort and Suricata are open-source signature IDS/IPS; Zeek is a network-analysis/behaviour monitor; OSSEC/Wazuh are host-based IDS with file-integrity monitoring; AIDE is a file-integrity checker. | Snort docs; Suricata docs; Zeek "About"; OSSEC site; AIDE site | no |
| A Snort rule = header (action, protocol, src IP/port, direction `->` or `<>`, dst IP/port) + options in parentheses. Actions: alert, log, pass, drop, block, reject, react, rewrite. | Snort 3 docs — Rule Headers and Rule Actions | no |
| Snort rule options: `msg` (alert text), `sid` (unique id; 1–999999 reserved, local rules start at 1000000), `rev` (revision), `classtype`, `content` (payload match), `flow` (e.g. established,to_server), `detection_filter` (rate). | Snort 3 docs — sid, classtype, flow, content, detection_filter | no |
| Suricata rule = action + header + options; actions alert/pass/drop/reject; default action-order pass, drop, reject, alert; largely Snort-compatible syntax with richer app-layer keywords (http.uri, http.method). | Suricata docs — rules intro, suricata.yaml action-order, http-keywords | no |
| Suricata can normalize HTTP (per-server "personality"/host-os-policy) and reassemble streams by target OS, which defeats many insertion/evasion tricks. | Suricata docs — suricata.yaml (libhtp personality, host-os-policy) | no |

## Honeypot Concepts and Detecting Honeypots

| Fact | Sources | verify |
|---|---|---|
| Honeypot = a decoy system or resource with no production use, made attractive to attackers; because it has no legitimate users, almost any interaction is suspicious, so alerts have few false positives. | NIST glossary "honeypot" (CNSSI 4009); NIST SP 800-94 §8.3.4 | no |
| Honeypots supplement, they do not replace, IDS/IPS and other controls; their legality should be reviewed before deployment, and skilled analysts should run them. | NIST SP 800-94 §8.3.4 | no |
| Interaction level: low-interaction (emulates a few services, cheap, limited data, easier to fingerprint) vs high-interaction (real OS/services, richest data, more risk of being used as a pivot). | Fortinet "what is a honeypot"; Kaspersky "what is a honeypot" | no |
| Purpose split: production honeypots (placed beside real servers to detect internal compromise) vs research honeypots (study attacker tools and trends in the wild). | Fortinet "what is a honeypot"; Kaspersky "what is a honeypot" | no |
| A honeynet is a network of honeypots; D3FEND distinguishes standalone (not connected to production), integrated (in the production environment), and connected honeynets. | Kaspersky "what is a honeypot"; MITRE D3FEND Standalone/Integrated Honeynet | no |
| Honeytokens / decoy credentials / decoy files (canary tokens) are non-system decoys: a fake credential, file, or URL that should never be used, so any use is an alert. | MITRE D3FEND Decoy User Credential / Decoy File; Canarytokens docs | no |
| Example honeypot tools: Cowrie (medium/high-interaction SSH/Telnet), Dionaea (traps malware over SMB/HTTP/FTP etc.), Conpot (ICS/SCADA), Honeyd (emulates many virtual hosts/OS personalities), KFSensor (Windows), T-Pot (all-in-one multi-honeypot platform). | Cowrie, Dionaea, Conpot, Honeyd, KFSensor, T-Pot project docs | no |
| Low-interaction decoys are the easiest to tell apart from production hosts; defenders keep decoys credible with realistic data and activity and by integrating them with normal assets. | MITRE D3FEND Decoy Environment / Integrated Honeynet; Fortinet "what is a honeypot" | yes |

## IDS/Firewall Evasion Countermeasures

| Fact | Sources | verify |
|---|---|---|
| Deny-by-default firewall policy plus ingress and egress filtering: block invalid/spoofed and RFC 1918 private source addresses at the perimeter; egress filtering (BCP 38 / RFC 2827, RFC 3704) stops spoofed outbound traffic and blind evasion. | NIST SP 800-41 Rev. 1 §4.1; RFC 2827 (BCP 38); RFC 3704 | no |
| Block/limit IP source-routing and rarely-needed IP options; drop overlapping/tiny fragments or reassemble them before inspection. | NIST SP 800-41 Rev. 1 §4.1.1; RFC 7126 (IP options); RFC 1858; RFC 5722 | no |
| Defeat insertion/evasion with traffic normalization and target-based reassembly: a normalizer rewrites ambiguous traffic to one interpretation before the IDS sees it; Snort frag3 and Suricata host-os-policy do this per destination OS. | Handley/Paxson USENIX "Network Intrusion Detection: Evasion, Traffic Normalization…"; Snort frag3; Suricata host-os-policy | no |
| Inspect encrypted traffic (TLS decryption at a proxy/NGFW) or add host-based sensors so the IDS is not blind to VPN/TLS/SSH payloads. | NIST SP 800-94 §4.3.5; NIST SP 800-41 Rev. 1 §2.3 | no |
| Use layered detection (signature + anomaly + protocol analysis) and multiple IDPS types (NIDS + HIDS + NBA); tune thresholds, blacklists/whitelists and keep signatures updated to cut false negatives. | NIST SP 800-94 §2.3, §2.4, §8.4 | no |
| Tune to reduce evasion via blinding: sensors should recognize DoS/blinding tools and shed that load; select failure-resistant products. | NIST SP 800-94 §4.3.3 | no |
| Detect tunnelling with network/DNS traffic analysis (odd DNS volume, beaconing, non-standard protocols) and filter egress to only required protocols. | MITRE D3FEND Network/DNS Traffic Analysis; ATT&CK M1037 Filter Network Traffic, M1031 Network Intrusion Prevention | no |
| Segment the network and put public services in a DMZ/screened subnet so a perimeter bypass does not reach the internal LAN; review firewall rulesets under change control. | NIST SP 800-41 Rev. 1 §3, §4; ATT&CK M1030 Network Segmentation | no |
| Deploy honeypots/decoys and canary tokens as high-signal tripwires that fire when perimeter controls are bypassed. | NIST SP 800-94 §8.3.4; MITRE D3FEND Decoy techniques; Canarytokens | no |
