# Research: M17 Hacking Mobile Platforms

Scope: the five sections in `content/modules/m17/meta.json`. The public CEH v13 course page lists the module's
key topics (OWASP Top 10 Mobile Risks 2024, anatomy of a mobile attack, app sandboxing issues, SMiShing, call
spoofing, OTP / 2FA hijacking, camera and microphone capture, Android rooting, jailbreaking iOS, MDM, mobile
security guidelines and tools). That list is used for scope only; all wording below is ours, from public
primary sources. The module is written from a defender's angle: what each attack surface is, how to recognize
it and how the platforms and the enterprise defend it. No attack walkthroughs.

Every fact was checked against at least two independent sources. **verify** marks EC-Council-specific lists or
labels and facts backed by a single source.

Checked on 2026-09-24. URLs tested with curl and a browser User-Agent. Notes on sources:
- owasp.org risk pages for the Mobile Top 10 (`/2023-risks/...`) now return 404 (site migration); the list and
  the risk pages are cited from the project's GitHub repo `OWASP/www-project-mobile-top-10`, which is what the
  site was built from. The project home page on owasp.org still answers 200.
- developer.android.com and source.android.com answer 302 to curl without cookies (auto sign-in redirect) and
  redirect missing pages to a parent page with status 200; they were checked with cookies enabled and by page
  title. Two guessed pages (`risks/backup`, `risks/sms`) do not exist and were dropped.
- fcc.gov sits behind Akamai (403 for any path); the pages kept were confirmed with the Wayback CDX API
  (juice jacking, spoofing, call authentication, cell phone fraud). `port-out-fraud-sim-swapping` has no
  archived 200 and was dropped.
- NIST glossary slugs that do not exist (404): jailbreaking, rooting, sideloading, code_signing, app_vetting,
  containerization, smishing, bluesnarfing, bluejacking, remote_wipe. The slug `jailbreak` exists but defines an
  **AI prompt jailbreak** (NIST AI 100-2), not a phone jailbreak; it is cited only for that distinction.
- Apple developer pages are rendered by JavaScript; their text was read through Apple's documentation JSON.

## Mobile Platform Attack Vectors

| Fact | Sources | verify |
|---|---|---|
| OWASP Mobile Top 10 2024 (final): M1 Improper Credential Usage, M2 Inadequate Supply Chain Security, M3 Insecure Authentication/Authorization, M4 Insufficient Input/Output Validation, M5 Insecure Communication, M6 Inadequate Privacy Controls, M7 Insufficient Binary Protections, M8 Security Misconfiguration, M9 Insecure Data Storage, M10 Insufficient Cryptography. | OWASP Mobile Top 10 project page; GitHub `2023-risks/index.md` (titled "OWASP Mobile Top 10 2024 - Final Release") | no |
| 2016 list for comparison: M1 Improper Platform Usage, M2 Insecure Data Storage, M3 Insecure Communication, M4 Insecure Authentication, M5 Insufficient Cryptography, M6 Insecure Authorization, M7 Client Code Quality, M8 Code Tampering, M9 Reverse Engineering, M10 Extraneous Functionality. In 2024, code tampering and reverse engineering merge into M7; authentication and authorization merge into M3. | OWASP project page (2016 list); GitHub `2016-risks/` folder | no |
| M1: hardcoded credentials, credentials sent unencrypted, credentials stored insecurely, weak authentication. M2: vulnerable or malicious third-party components, rogue insiders, weak build pipeline. M3: IDOR, hidden endpoints without authorization, roles sent by the client, local-only authentication. | GitHub risk pages m1, m2, m3; Android "Hardcoded cryptographic secrets" risk page | no |
| M5 threat agents: someone on the same (compromised) Wi-Fi, rogue carrier or network devices, malware on the device; vectors: deprecated protocols, accepting bad certificates, TLS on only some flows. M7: reverse engineering and code tampering (removing license checks, repackaging with malware); defense: obfuscation, integrity checks, server-side enforcement; "no fully reliable mechanism". | GitHub risk pages m5, m7; Android "Unsafe X509TrustManager" risk page; R8 app optimization page | no |
| M8: debug features left in release builds, cleartext HTTP allowed, world-readable files, exported components. M9: unencrypted local data, data in logs, backups. M10: weak algorithms, short keys, poor key management, no salting. | GitHub risk pages m8, m9, m10; Android "android:debuggable" and "Log info disclosure" risk pages | no |
| Smishing is phishing by SMS; FTC advice: don't click, forward spam texts to 7726 (SPAM) and report in the messaging app. MITRE ATT&CK Mobile T1660 Phishing covers SMS and messaging lures. | FTC "How to recognize and report spam text messages"; MITRE T1660 | no |
| Caller ID spoofing = deliberately falsifying caller ID; STIR/SHAKEN authenticates caller ID for calls over IP networks. | FCC "Caller ID spoofing" (archived 2025-03); FCC "Call authentication" (archived 2026-09) | no |
| SIM swapping / port-out fraud moves the victim's number to an attacker's SIM so SMS codes reach the attacker (MITRE T1451). SMS-reading malware steals OTPs (T1636.004 Protected User Data: SMS Messages; T1582 SMS Control). Defenses: carrier account PIN, move away from SMS MFA to FIDO. | FCC "Cell phone fraud" (archived 2025-06); MITRE T1451, T1636.004; CISA Mobile Communications Best Practice Guidance (2025 update) | no |
| NIST SP 800-63B-4 lists PSTN (SMS/voice) out-of-band authentication as the one "restricted" authenticator. | NIST SP 800-63B-4; CISA guidance ("do not use SMS as a second factor") | no |
| Juice jacking: malware on public USB charging stations; use an AC outlet or a charge-only cable. MITRE T1458 Replication Through Removable Media describes attacks over a malicious charging station or PC. | FCC "Juice jacking" (archived 2025-11); MITRE T1458 | no |
| Camera/microphone capture: MITRE T1429 Audio Capture and T1512 Video Capture; since Android 9 idle background apps lose sensor access, which malware counters with a foreground service (T1541 Foreground Persistence); Android 12+ shows status-bar microphone/camera indicators. | MITRE T1429, T1512, T1541; Android 12 "Behavior changes: all apps" | no |
| Overlay / GUI input capture (fake login screens over a real app, MITRE T1417.002) and tapjacking; Android 12 blocks touches through untrusted overlays from another UID; apps can set `filterTouchesWhenObscured`. | MITRE T1417.002; Android "Tapjacking" risk page | no |
| "Anatomy of a mobile attack" splits the attack surface into the device (browser, SMS/phone, apps, OS), the network (Wi-Fi, rogue AP, MITM, SSL stripping) and the data center / cloud (web server, database). | EC-Council course page (topic name only); NIST Mobile Threat Catalogue categories (application, cellular, LAN/PAN, ecosystem, supply chain...) | **yes** (EC framing, tag `ec-council-specific`) |
| "App sandboxing issues": a sandbox limits each app to its own data and resources; an app that escapes it or is over-permissioned can read other apps' data. | Android "Application Sandbox"; Apple "Security of runtime process"; NIST glossary "sandbox" | no (EC topic label is `ec-council-specific`) |

## Hacking Android OS

| Fact | Sources | verify |
|---|---|---|
| Android gives each app a unique Linux UID and runs it in its own process: a kernel-level sandbox (DAC). SELinux adds MAC; since Android 9 each non-privileged app targeting API 28+ runs in its own SELinux sandbox. | AOSP "Application Sandbox"; AOSP "Security-Enhanced Linux in Android" | no |
| Permissions: install-time (normal), runtime (dangerous, requested at run time since Android 6.0 / API 23) and special permissions (e.g., drawing over other apps). | Android "Permissions on Android"; "Request runtime permissions" | no |
| APK signing: v1 (JAR), v2 (Android 7.0), v3 (Android 9, key rotation), v4 (Android 11, incremental). Android uses self-signed certificates and does not check a CA. `apksigner verify --print-certs` shows the signing certificates. | AOSP "App signing"; Android "apksigner" | no |
| Sideloading = installing apps from outside Google Play; Android blocks it until the user allows "install unknown apps" for the source. Google Play Protect scans apps, including those from other sources. | Android "Alternative distribution options"; Google Play Help "Use Google Play Protect"; CISA guidance | no |
| Rooting gives the user (or malware) root, bypassing built-in restrictions; organizations should treat such devices as untrusted. It usually requires an unlocked bootloader. | NIST SP 800-124r2 §3.1.7; AOSP "Verified Boot / device state" | no |
| Verified Boot: chain of trust from a hardware root of trust through bootloader to boot, system and vendor partitions (dm-verity), with rollback protection. Boot-screen states: ORANGE = bootloader UNLOCKED, YELLOW = locked with custom root of trust, RED = verification failure. | AOSP "Verified Boot"; AOSP "Boot flow" | no |
| Play Integrity API verdicts: MEETS_DEVICE_INTEGRITY (genuine certified device), MEETS_BASIC_INTEGRITY (basic checks only; bootloader may be unlocked), MEETS_STRONG_INTEGRITY (plus recent security updates on Android 13+), and app verdict PLAY_RECOGNIZED / UNRECOGNIZED_VERSION. | Android "Integrity verdicts"; Android "Play Integrity API" overview | no |
| ADB: client, server and daemon (adbd). `adb tcpip 5555` switches a device to TCP; emulators use ports 5554-5585; since Android 4.2.2 the device asks the user to accept the computer's RSA key. | Android "Android Debug Bridge (adb)"; MITRE T1458 | no |
| Manifest risks: `android:debuggable="true"` in release; `android:allowBackup` defaults to true (up to 25 MB to the cloud); components with intent filters must declare `android:exported` explicitly when targeting Android 12+; exported=true lets any app launch them. | Android risk pages "android:debuggable" and "android:exported"; Android "Auto Backup"; Android 12 behavior changes | no |
| Network security config: cleartext disabled by default for apps targeting Android 9 (API 28)+; apps targeting 7.0+ trust only system CAs by default (not user-added); `<pin-set>` pins certificates. | Android "Network security configuration"; Android "Security with network protocols" | no |
| Android Keystore keeps key material out of the app process and can bind keys to secure hardware (TEE, StrongBox on Android 9+). | Android "Android Keystore system"; AOSP "Hardware-backed Keystore" | no |
| File-based encryption with Credential Encrypted (after unlock) and Device Encrypted (Direct Boot) storage; required on new devices from Android 10; FDE only up to Android 9. | AOSP "File-based encryption"; AOSP "Encryption" | no |
| Android analysis tools: apktool (decode and rebuild APK resources), jadx (DEX to Java decompiler), dex2jar, Androguard, drozer (tests apps' IPC endpoints), MobSF (static and dynamic analysis), Frida / objection (runtime instrumentation). | GitHub repos (descriptions); Kali tool pages (apktool, jadx, dex2jar); OWASP MASTG tools | no |
| EC-Council's Android lab list (binary payloads, ADB exploitation, malicious APK) and named offensive tools. | EC-Council course page | **yes** (scope only; not reproduced) |

## Hacking iOS

| Fact | Sources | verify |
|---|---|---|
| Secure boot: the Boot ROM is immutable hardware root of trust holding the Apple Root CA public key; it verifies iBoot, which verifies the kernel. | Apple Platform Security "Boot process for iPad and iPhone"; Apple "Secure Enclave" | no |
| Mandatory code signing: all executable code must be signed with an Apple-issued certificate; blocks unsigned code and self-modifying code. | Apple "App code signing process"; Apple "App security overview" | no |
| Every third-party app is sandboxed with a randomly assigned home directory; access to other data only through system services; entitlements; ASLR. | Apple "Security of runtime process"; NIST glossary "sandbox" | no |
| Data Protection classes: A Complete Protection, B Protected Unless Open, C Protected Until First User Authentication (default), D No Protection; keys derived from passcode + device UID. | Apple "Data Protection classes"; Apple "Data Protection overview" | no |
| Keychain stores small secrets (passwords, tokens) with its own protection classes; Secure Enclave is an isolated subsystem for keys and biometrics. | Apple "Keychain data protection"; Apple developer "Keychain services" | no |
| ATS: TLS 1.2+, forward secrecy (ECDHE), RSA ≥ 2048 or ECC ≥ 256, SHA-256+ certificates; blocks non-compliant connections. | Apple developer "Preventing insecure network connections"; OWASP MASTG network chapter | no |
| App Attest (DeviceCheck) proves requests come from a genuine instance of the app, key in the Secure Enclave. | Apple developer "Establishing your app's integrity"; MITRE M1002 Attestation | no |
| Jailbreaking removes iOS security layers: security vulnerabilities, instability, battery drain, inability to install updates; Apple may deny service. | Apple "Unauthorized modification of iOS"; NIST SP 800-124r2 §3.1.7 | no |
| Jailbreak types: tethered, semi-tethered, untethered, semi-untethered (and exploit levels bootrom / iBoot / userland). | EC-Council framing; no primary vendor source | **yes** (`ec-council-specific`) |
| Lockdown Mode: optional extreme protection for people targeted by mercenary spyware; blocks most message attachments, link previews, some web technologies, and prevents installing configuration profiles or MDM enrollment. | Apple "About Lockdown Mode"; Apple Platform Security "Lockdown Mode security"; CISA guidance (enable Lockdown Mode) | no |
| Trustjacking: abuse of the "Trust This Computer" pairing (Wi-Fi sync) to reach an iPhone later. | EC-Council topic; no primary vendor source | **yes** (`ec-council-specific`) |

## Mobile Device Management

| Fact | Sources | verify |
|---|---|---|
| MDM = administration of mobile devices, usually through a third-party product; EMM = umbrella for policy deployment and device monitoring (MDM + MAM + more). | NIST glossary "mobile device management", "enterprise mobility management"; NIST SP 800-124r2 §4.2 | no |
| EMM policy: manage Wi-Fi/Bluetooth/NFC, restrict camera and copy/paste, detect baseline changes, block access by OS version or root/jailbreak status, disable developer mode. | NIST SP 800-124r2 §4.2.1; MITRE M1012 Enterprise Policy | no |
| MAM controls enterprise apps without enrolling the whole device (fits BYOD privacy): allowlists, restrict sideloading, app-level wipe, containerization. | NIST SP 800-124r2 §4.2.2; NIST SP 1800-22 (BYOD) | no |
| MTD = on-device agent detecting malicious apps, network attacks (MitM), phishing, misconfigurations, OS/app vulnerabilities; integrates with EMM for automatic response. | NIST SP 800-124r2 §4.2.3; NIST glossary "mobile threat defense" | no |
| App vetting: tests apps against enterprise requirements before deployment (SP 800-163r1 process); VMI = virtual phone hosted in the back end; app wrapping; secure containers (app-based or OS-based). | NIST SP 800-163r1; NIST SP 800-124r2 §4.2.4-4.2.7 | no |
| Deployment models: strict enterprise use (fully managed/GFE), COPE (company owns, personal use allowed), BYOD, CYOD (employee buys from an approved list). | NIST SP 800-124r2 §5.1.3; NIST glossary "COPE"; NIST SP 1800-21 (COPE) | no |
| Remote wipe: full-device wipe (company devices) vs enterprise/selective wipe (BYOD). Needs power and network; not a sole control. | NIST SP 800-124r2 §4.3.3; Apple Platform Deployment "Intro to device management" | no |
| Android Enterprise: work profile on personally owned device (profile owner), work profile on company-owned device, fully managed device (device owner), dedicated device (kiosk). DPC = the device policy controller app. | Android Enterprise terminology; Android "Work profiles"; Google "What is an Android Work Profile?" | no |
| Apple: supervision = organization-owned device with more control (Automated Device Enrollment); User Enrollment = BYOD, limited payloads, manages only the organization's accounts and data. | Apple Platform Deployment "About device supervision"; "User Enrollment and device management" | no |
